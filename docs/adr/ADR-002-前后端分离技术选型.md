# ADR-002 · 前后端分离技术选型：React 前端 + FastAPI 后端

> 编号：ADR-002 ｜ 日期：2026-08-14 ｜ 状态：**已确认**
> 关联需求：PRD-001 §五 非功能需求修订（5.1 服务化方向）；未来服务化轨迹（用户登录、多 profile、个性化）

## 背景

当前 `site/` 是纯 HTML+JS 静态站：数据以全局变量注入、`app.js` 用模板字符串拼 HTML，数据与渲染混杂，无类型、无模块边界、难维护（见 `docs/tech/网站.md` 记录的旧架构）。同时产品长线目标是演进为**可部署服务**（未来：用户注册登录、多 profile、个性化定制），需要一个能承载后端、数据库、鉴权的架构。本阶段只做**前后端分离**，登录/多用户/数据库不在本阶段实现，但选型必须为其预留空间。

## 决策

**前端用 React 18 + TypeScript + Vite（SPA）；后端用 Python FastAPI；前后端以 OpenAPI 为契约；本阶段内容由后端直接提供（不引入数据库），浏览器状态暂留 localStorage。**

- **前端**：React 18 + TS + Vite，React Router 路由；程序化 SVG（`scenes.js`/`maps.js` 的算法与视觉）机械移植为 TS 模块，**不重写**；构建产物为静态目录，dev 阶段由 Vite 代理 `/api` 到后端。
- **后端**：Python FastAPI，Pydantic 模型（字段依 `docs/tech/数据契约.md`）；内容数据由现有 data 文件转成 JSON，后端启动加载进内存提供 API。
- **契约**：FastAPI 自动生成 OpenAPI，前端用 openapi-typescript 生成 TS 类型——前后端数据契约必然一致，替代手写类型。
- **本阶段边界**：不引入数据库（后端读 JSON 即够）；用户状态（gear/tasks/badges/plans:done）暂留 localStorage；等账号/DB 阶段再迁后端。登录、多用户、个性化不做。
- **旧站过渡**：`site/` 保留至新站功能对齐后退役。

## 放弃的备选方案

| 方案 | 放弃原因 |
|---|---|
| 后端用 Node/TypeScript（Fastify/Express + tRPC） | 用户明确要求后端用 Python |
| Next.js 前后端一体 | 用户要「前后端分离」的明确边界；且 SSR 与「程序化 SVG 客户端生成」的契合度低 |
| Django 后端 | 全家桶偏重；本阶段只需内容 API，FastAPI 更轻、自动出 OpenAPI 文档 |
| 正式 monorepo（pnpm workspaces 等） | 本规模只需同仓库 `web/`+`backend/` 两目录 + 契约，无需多包独立发布 |
| 本阶段就上数据库 | 内容仍是静态的（24 计划 + 路线/路网），无用户态，引入 DB 纯增复杂度；DB 留到登录/多用户阶段 |
| 前端 JS（不引 TS） | 可维护性是本次改造的核心动机，TS 类型是根治「无类型」的手段 |

## 风险与边界

- **离线/双击即用的形态放弃**：改为需要 Node 构建（前端）+ Python 运行（后端），是服务化方向下的必然取舍（PRD-001 §5.1 已据此修订）。
- **隐私红线**：`config/profile.json`、`backend/data/profile.json` 均 gitignore，真实画像信息仍不入库、不入 git；后端是配置的新读取方。
- **NETWORK 2MB**：前端需一次性拉取路网数据，本阶段（本地 dev）可接受；未来多用户/规模化时按 bbox 裁剪。
- **路线流水线（Node）保留**：仍是内容生成器，产物经 `tools/export-content.js` 转成后端 JSON，不重写。
