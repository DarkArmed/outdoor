# ADR-003 · 后端服务化与多用户：PostgreSQL + FastAPI + JWT

> 编号：ADR-003 ｜ 日期：2026-09-12 ｜ 状态：**已确认**
> 关联需求：PRD-001 §五（服务化方向）；PRD-004（多用户与方案/出行计划解耦）

## 背景

ADR-002 已确认前后端分离技术选型（React + TS + Vite / FastAPI），并约定本阶段不引入数据库、登录、多用户。但项目长期目标是演化为可部署服务，后续需要支撑小程序、移动端及多家庭使用。用户明确决定：**后端一步到位实现服务化**，前端 `site/` 本次不动，作为过渡期消费者。

## 决策

**后端直接升级为完整服务：Python FastAPI + PostgreSQL + SQLAlchemy 2.0 + Alembic + JWT 认证；公共方案（Plan）与用户出行计划（Trip）解耦，采用快照机制。**

- **数据库**：PostgreSQL。关系模型清晰，便于表达用户、方案、出行计划、路线、状态之间的关联；后续小程序/移动端可直接复用同一套 API 与数据库。
- **ORM 与迁移**：SQLAlchemy 2.0 + Alembic，保证模型与数据库结构一致、可迁移。
- **认证**：JWT（OAuth2 Password Bearer）。无状态、通用，便于未来小程序通过同一接口认证；第一阶段 `site/` 不接入登录，但后端 API 已具备能力。
- **方案/出行计划解耦**：
  - `plans` 表保存**公共方案**，由现有 `PLANS` 导入，可随赛季持续更新。
  - `trips` 表保存**用户出行计划**，用户采用某方案时生成一条 trip，深拷贝方案内容为 `snapshot`，同时保留 `overrides` 供用户个性化覆盖。
  - 方案后续更新不影响已有 trip；未来可提供「同步到最新方案」功能。
- **用户数据持久化**：gear / tasks / checkin / badges 全部存数据库，不再依赖 `localStorage`。
- **前端范围**：`site/` 完全不动，第二阶段再重写 React 前端并接入后端 API。

## 放弃的备选方案

| 方案 | 放弃原因 |
|---|---|
| 第一阶段仍用 JSON 文件内存存储 | 无法满足多用户、持久化、解耦需求，后续还得推倒重来 |
| SQLite 替代 PostgreSQL | 本地零依赖更简单，但多用户并发、迁移工具、运维工具弱于 PostgreSQL；如部署受限可降级 |
| Session Cookie 认证 | 有状态、跨域/小程序场景不如 JWT 通用 |
| 方案与出行计划不分离，直接共用同一张表 | 多用户采用同一方案时无法保留各自覆盖项，且方案更新会意外影响历史出行计划 |
| 不引入快照，trip 直接引用 plan 当前内容 | 方案优化/季节调整会导致历史出行计划内容突变，用户体验不可控 |

## 风险与边界

- **前端未接入**：第一阶段后端服务孤立运行，需通过 `/docs`、curl 或测试验证；`site/` 仍走原有静态数据。
- **隐私红线**：真实家庭住址、孩子真名等画像信息仍不入 git，只存运行期数据库。
- **路线重新生成**：`routes` 表初始导入现有 `ROUTES` 数据；用户 home 变化后重新生成路线是后续增强，本阶段先直接复用已有路线。
- **NETWORK 体积**：路网约 2MB，一次性提供；后续可按 bbox/区域切片。
- **默认用户迁移**：运行 seed 时从 `config/profile.json` 创建首个用户 + 画像，仅用于初始化，不提交真实数据。
