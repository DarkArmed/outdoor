# 数据流水线（pipeline）

> v1.0 · 2026-10-17

把攻略语料采集从「手动跑脚本」升级为**常驻、可调度的生产级流水线**：worker 常驻进程按 DB 作业表轮询调度，调用 guide-pipeline 引擎执行采集，请求预算与风控状态全部落库，管理员通过 /admin 后台监控与控制。需求见 PRD-008；部署形态与调度选型理由见 ADR-008；采集节奏（24h 一轮 / 会话预算 / 冷却递增）依据调研 INV-001（小红书采集窗口规律）。

## 一、定位与架构总览

```
┌─ pipeline worker（独立常驻进程/容器）────────────────────┐
│  Scheduler（DB 轮询，默认 30s tick）                     │
│    └─ 到期作业 → 线程池执行 → stages 注册表取阶段        │
│         └─ collect 阶段：进程内加载 guide-pipeline 引擎  │
│              ├─ 语料/事件 → corpus/ + events.jsonl       │
│              └─ 事件双写 → DB PipelineEvent（预算台账）  │
└──────────────────────────────────────────────────────────┘
        ↑ 共用同一个 PostgreSQL（不引入新组件）
┌─ app（FastAPI，不持有 Scheduler）────────────────────────┐
│  Admin API /api/admin/pipeline/*（get_current_admin）    │
│  web /admin dashboard（仅 is_admin 可见）                │
└──────────────────────────────────────────────────────────┘
```

- **与 guide-pipeline 的分工**：引擎（`tools/guide-pipeline/`）管「怎么采」——源适配器、限速、登录 cookie、语料落盘（见 [攻略流水线.md](攻略流水线.md)）；数据流水线（`backend/app/pipeline/`）管「什么时候采、采多少、失败了怎么办」——调度、预算账本、冷却节奏、监控后台。collect 阶段用 importlib 按文件加载引擎 `pipeline.py`，通过包装引擎 EventBus 挂 DB sink（默认 JSONL sink 保留），用作业 policy 的 `session_budget` 覆盖引擎 config 值。
- **单实例**：PRD 明确不做多 worker；同一作业不重入（内存锁 + 执行前预推 `next_run_at` 双保险）。API 进程不含调度循环，`trigger` 只是把 `next_run_at` 拨到当前时间，由 worker 下个 tick 拾起。

## 二、调度机制

**tick**（`Scheduler.tick`，`backend/app/pipeline/scheduler.py`）：

1. `state='cooldown'` 且 `cooldown_until` 到期 → 自动回 `active`，排到下一个 `run_at` 窗口；
2. `enabled` 且 `state='active'` 且 `next_run_at` 到期 → 提交线程池执行（Playwright 同步阻塞跑在 worker 线程，主循环不阻塞）；
3. `paused` / `disabled` 跳过。

tick 间隔默认 30s（配置项 `pipeline_tick_seconds`）。优雅退出：收到 SIGTERM/SIGINT 后不再启新轮，等正在跑的作业完成（采集轮次有预算上限、时长可控，强断会留下未完结的 PipelineRun 与半成品语料目录）。

**作业状态机**：`state ∈ active / paused / cooldown` + 独立开关 `enabled`。

- pause：`enabled=False`；`active → paused`；**cooldown 中暂停保留 `state=cooldown`**——冷却剩余时长是风控结果，暂停不应抹掉它。
- resume：`enabled=True`；`paused → active`；cooldown 未到期仍回 cooldown（到期由调度器自动恢复），已过期则回 active 并清掉 `cooldown_until`。
- trigger：paused/disabled 或 cooldown 中的作业返回 409（风控冷却不手动绕过）。

**结局 → 下次运行**（`policies.next_schedule`，纯函数便于单测）：

| 结局 | 含义 | 处理 |
|---|---|---|
| `clean` / `budget_stop` | 正常跑完 / 预算内主动收工 | 下一个本地 `run_at` 窗口（默认 08:30）；streak 计数清零（预算内收工说明账号状态健康，信用恢复） |
| `streak` | 3 连空 / SourceBlocked | streak+1，冷却 `min(24h × 2^(streak-1), 48h)`（第 1 次 24h、第 2 次起 48h 封顶）；`state → cooldown`，下次窗口为冷却结束后的第一个 `run_at` |
| `frozen` | 引擎层「当日已有 blocked 拒跑」（既有风控记录的余波，非新风控证据） | **不增加 streak**；冷却未结束 → 重排到冷却结束后的下一个窗口；无冷却记录 → 排到下一个常规窗口 |
| `error` | 阶段执行异常 | 1h 后重试；连续 error 不放大，streak/冷却保持原值 |

`run_at` 为本地时区 `HH:MM`（作业 policy 配置，非法值回退 08:30）；`next_run_at` / `cooldown_until` 落库为 UTC，SQLite 读出的 naive datetime 统一按 UTC 补齐再比较（`policies.as_utc`）。

## 三、预算账本（PipelineEvent）

事件级台账（ADR-008 决策 5）：引擎发射的每个事件（`search` / `detail_attempt` / `saved` / `failed` / `blocked` / `stopped` / `failed_engine` …）经 DB sink 写入 `pipeline_events`（带 `job_id` / `run_id` / `source` / `payload`），同时保留引擎默认的 `events.jsonl` 输出（向后兼容既有批次工具）。这解决了旧批次脚本「无跨批次统一额度账本」的缺口。

- **24h 滑动窗口预检**：启动某源前，按 `event ∈ (search, detail_attempt)` 求该源 24h 内请求数（`budget_used_24h`）；达到作业 `session_budget` 即跳过该源，记 `stopped reason=budget_stop`，本轮不再请求。
- **当日 blocked 拒跑**：24h 内该源已有 `blocked` 记录（`blocked_within_24h`）→ 不启动引擎，记 `stopped reason=source_paused_for_today`，结局归类 `frozen`。
- **限额来源兜底顺序**（dashboard overview 用）：引擎 config `rate_limits[<源>].daily_cap` → `rate_limits.default.daily_cap` → 含该源的作业中最大的 `session_budget`（`limit_source` 分别标注 `engine_config` / `job_policy`）。

## 四、队列排序与提前收工

- **关键词队列按历史尝试次数升序**：以 PipelineEvent `event='search'` 的 `payload.keyword` 计数，尝试少的优先；次数相同保持原顺序（稳定排序）。关键词取自作业 `policy.keywords`，缺省用引擎 config 目的地组关键词。避免预算消耗在反复落空的目标上（INV-001 队列规则）。
- **详情连续失败提前收工**：同一源连续 3 次详情 `failed`（`EARLY_STOP_DETAIL_FAILURES`）即中断本轮该源，记 `stopped reason=detail_failure_stop`。结局归类为 `budget_stop` 而非 `streak`——INV-001 把详情超时/失败视为预算见底前兆，主动收工是健康行为，不应触发冷却递增。引擎没有中途停止钩子，由事件 sink 抛内部异常中断主循环，引擎 try/finally 正常关闭浏览器，已落盘事件不丢。
- **结局归类**（`_classify`）：跨源取最严重——`streak` > `frozen` > `budget_stop` > `clean`；引擎进程级异常记 `failed_engine` 事件并继续其余源，若无更差信号则结局为 `error`。

## 五、三张表的角色

字段级契约见 [数据契约.md §六](数据契约.md#六后端数据库实体新增)，这里只讲机制与关系：

- **`pipeline_jobs`**：作业定义与调度状态——类型（阶段注册表键）、policy（sources / session_budget / run_at / interval / keywords）、enabled、state、`next_run_at` / `last_run_at`、冷却与 streak 计数。一个作业 1:N 多次运行。
- **`pipeline_runs`**：每次执行的一行记录——起止时间、结局、本轮请求数 / 保存数 / 详情失败数、异常摘要。
- **`pipeline_events`**：请求与信号的事件台账——预算计量、队列排序、blocked 拒跑的唯一口径来源，挂 `job_id` / `run_id` 关联到作业与运行。三表均 `ondelete=CASCADE` 随作业删除。

## 六、运行方式

```bash
# 本机（backend/ 目录，依赖后端 .env 的 DATABASE_URL）
python -m app.pipeline.worker

# 容器（compose 第三个常驻服务，Dockerfile.worker）
docker compose --env-file deploy/.env.local -f deploy/compose.yaml up -d pipeline
docker compose --env-file deploy/.env.local -f deploy/compose.yaml logs -f pipeline
```

- worker 启动时 `ensure_default_jobs` **幂等 upsert** 两个默认作业：同名作业已存在则跳过，不覆盖后台改过的参数。
  - `collect.xhs_daily`：sources=[xhs]，会话预算 25，每 24h，08:30（INV-001 节奏内置）；
  - `collect.others_daily`：sources=[weibo, ctrip, visitbeijing]，预算 150（参考引擎 config 的 daily_cap），09:30 错开。
- worker 镜像基于 Playwright 官方 Python 镜像（自带 Chromium，Python 包与浏览器版本锁死），非 root 用户 `pwuser` 运行；挂载 `../corpus`（语料）与 `tools/guide-pipeline/.cookies`（登录 cookie，读写持久化）。配置项：`PIPELINE_TOOLS_DIR`（引擎目录覆盖）、`PIPELINE_CORPUS_ROOT`（语料根目录，借道 `GUIDE_PIPELINE_CORPUS_ROOT` 传给引擎）。
- worker 无 HTTP 端口，healthcheck 校验 PID 1 是调度进程本身；日志走 docker json-file（10MB × 3 滚动）。
- **管理员开通**：`python -m app.promote_admin <email>`（`--demote` 撤销；容器内用 `docker compose ... exec app python -m app.promote_admin`，见 [操作手册.md](操作手册.md)）；后台入口 web `/admin`（前端 `RequireAdmin` 拦非管理员，API 侧 `get_current_admin` 强制）。

## 七、扩展指南

**加新源**（采集能力在引擎侧）：

1. 在 `tools/guide-pipeline/sources/` 新增适配器并在 `sources/__init__.py` 用 `register_adapter(name, cls)` 自注册（不动 `pipeline.py` 入口，详见 [攻略流水线.md](攻略流水线.md) 与引擎 README）；
2. 把源名加入作业 `policy.sources`（后台 PATCH 作业或直接改库），调度与预算台账自动生效。

**加新阶段**（流水线侧）：

1. 在 `backend/app/pipeline/stages/` 新增模块：继承 `Stage` 实现 `run(ctx) -> StageOutcome`，模块底部 `register_stage("<type>", Cls)`；
2. 在 `stages/__init__.py` 加 import（导入即注册，调度器/worker 只 import 本包，核心不动）；
3. 建一个 `type` 为该值的 PipelineJob（默认作业或后台）即被调度。

本期 `process` / `consume` / `emit` 已注册但为占位实现：发射 `skipped` 事件并返回 `clean`（emit 的产出交接点见 PRD-007，不在本期实现）。`StageContext` 提供 `db` / `job` / `run` / `emit()`（写 PipelineEvent）；`StageOutcome` 携带结局与计数，调度器据此重排。

## 八、Admin API 端点清单

前缀 `/api/admin/pipeline`，全部要求 `get_current_admin`（`users.is_admin`）。字段契约见 schemas，以下为指针级清单：

| 方法与路径 | 作用 |
|---|---|
| `GET /overview` | 监控总览：全部作业 + 各源预算用量（24h）/ 限额 / 冷却标记 |
| `GET /runs` | 运行记录列表（`job_id` / `skip` / `limit`，按开始时间倒序） |
| `GET /events` | 事件台账查询（`source` / `event` 过滤，按时间倒序） |
| `POST /jobs/{id}/pause` | 暂停（cooldown 中暂停保留冷却，见第二节） |
| `POST /jobs/{id}/resume` | 恢复（cooldown 未到期仍回 cooldown） |
| `POST /jobs/{id}/trigger` | 立即触发（拨 `next_run_at` 到现在；paused/cooldown 返回 409） |
| `PATCH /jobs/{id}` | 改参数：`session_budget`（1–200）/ `run_at`（HH:MM）/ `interval`（如 `24h`）/ `name`；`reschedule=true` 时按新 `run_at` 重排（cooldown 中排到冷却结束后的窗口） |
