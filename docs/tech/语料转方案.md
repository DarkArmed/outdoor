# 语料转方案

> 版本：v1.1 ｜ 日期：2026-10-11（V1–V8 全部验证通过）

关联需求：PRD-007（语料转出行方案）；上游语料机制见 [攻略流水线](攻略流水线.md)；输出字段遵循 [数据契约](数据契约.md) §二 PLANS。

## 一、背景

PRD-006 一期（语料采集）已落地：本地语料库 `corpus/` 存有 400+ 条北京周边户外攻略原文（小红书/微博/携程/北京旅游网），含全文、原图与互动数据。采集解决了「素材从哪里来」，但语料仍是不可直接使用的原文堆：

- 现有方案（`plans/` 与 `data/data-*.js`）全部来自 AI 规划生成，风格与地点逐渐重复——这正是 PRD-006 立项要解决的问题，一期只完成了一半；
- 语料是非结构化原文（攻略、随笔、游记、官方介绍混合），系统（网站/小程序/种子导入）只认 [数据契约](数据契约.md) §二的 PLANS 结构；
- 二期（PRD-006 §3 展望）要做的事：标准化抽取、语料筛选、与 `data/data-*.js` 方案格式对齐。本方案即二期的落地设计。

目标：**把语料库中的真实攻略，转换为系统可用的出行方案**（种子数据条目），并保证事实可溯源、文字合规原创、输出可被现有链路（dump-data → seed → API → 页面）消费。

## 二、现状

### 2.1 语料库（输入侧）

- 位置与结构：`corpus/raw/<source>/<id>/`，每条自包含：`meta.json`（标题/作者/链接/互动数据/媒体清单）、`text.md`（全文）、`images/`、`videos/`；全局索引 `corpus/index.jsonl`（source, id, title, keyword, destinations, url, fetched_at, n_images, n_videos, has_fulltext）。`corpus/` 整体 gitignore。
- 存量（2026-10-09）：561 条；visitbeijing 270、weibo 200、xhs 85、ctrip 6；359 个候选目的地已全部覆盖（10-08 批次 277 个 + 10-09 重试批次补齐 82 个）。小红书在两次批次中均因「连续空搜索结果」触发保守暂停（红线：当天不对抗），UGC 源补采效率明显低于官方源。
- 内容分布：8 个已有方案的主力目的地（白河湾、神堂峪等）各 8–11 条；**新目的地大多只有 1–3 条**，且不少相关内容挂在「泛主题-亲子徒步/露营/溯溪/自驾游/观星」组下，`destinations` 字段不含具体地名。
- 内容形态实测：
  - **小红书**：攻略结构化程度最高（自带时间线、门票、停车、适合人群、避雷），是主力料源；
  - **微博**：偏随笔，但有实况信息（距离、体感温度、人流），互动数据弱；
  - **携程**：长游记，带天数/出行人等元数据，但存量老、只有 6 条；
  - **北京旅游网**：官方介绍（地址、开放信息、电话），无体验细节，适合补「门票/开放状态」类硬事实。
- 选料坑（PoC 实测）：同一目的地别名多（喇叭沟门 = 喇叭沟 = 喇叭沟原始森林）；仅靠索引 `destinations` 会漏料，**必须结合全文检索**；全文检索会带来**误命中**（泛游记仅列名、同名/邻名景区），证据包须支持把误收录条目标记为 `excluded` 并说明理由，提取环节只引用有效条目。

### 2.2 方案数据链路（输出侧）

- 种子文件：`data/data-a|b|c|d.js`（a=9 月、b=10 月+备用、c=11 月、d=12 月），`PLANS.push({...})`；
- 导入链：`tools/dump-data.js`（Node vm 执行 data 文件导出 JSON）→ `backend/app/seed.py`（幂等：已存在 id 跳过，新 id 入库）→ `plans` 表 → API → web/小程序；
- 备用计划机制：`archived: true` 进首页「备用计划」区，路线流水线跳过；备用计划允许非日期 id（数据契约 §二）；
- 路线数据 `data/routes.js` 由路线流水线生成，依赖高德 key（`tools/route-pipeline/config.json`，gitignore，**本机当前未配置**）。无路线数据的计划页面自动回退卡通示意图——新方案可先生成数据、路线后补；
- 校验缺口：目前没有任何工具校验 data 文件是否符合数据契约（靠人肉），也没有 seed dry-run。

### 2.3 差距小结

| 缺口 | 影响 |
|---|---|
| 语料 → 方案无工具链 | 转换靠纯手工，无法批量、无法复用 |
| 无中间层契约 | 事实与出处脱节，无法审校「这句从哪来的」 |
| 无输出校验 | 不合规条目要到 seed 报错才发现 |
| 无合规检查 | 语料原文/作者信息有泄进种子数据的风险（PRD-006 §2.4 红线） |

## 三、业务流程

```
① 选目的地      从语料覆盖 + 赛季地点库选候选（优先无现有方案、当季可玩）
② 选料          按别名集在索引 + 全文检索语料 → 证据包（evidence bundle）
③ 结构化提取    LLM agent 读证据包 → 方案草稿（draft JSON，事实块带来源引用）
④ 审校          契约检查 + 安全审查（面向新手，强度保守）+ 原创性检查（不得抄原文）
⑤ 落盘          草稿 → data-e.js 追加 PLANS 条目（archived: true 备用计划）
⑥ 校验          dump-data 解析 + 数据契约字段校验 +（可选）seed dry-run
⑦ 入库          下次 seed 自动入 plans 表 → API → 页面备用计划区可见
⑧ 后续（本方案外）路线流水线补 routes.js；用户使用满意后排期成 plans/*.md 周计划
```

角色分工与原则：

- **LLM agent 负责 ③**（攻略非结构化，纯规则提取质量不可行；选型理由见 ADR-007）；
- **工具负责 ②⑤⑥**（确定性、可重复、可测试）；
- **用户终审 ④**：新方案一律 `archived: true`，不自动排期，人看过才用；
- **安全原则**：面向户外小白——强度取语料中偏弱的一档（PoC 例：喇叭沟门登顶线 12.2km/爬升 820m 超出 7 岁耐力，方案只取景区浅层步道 3km）、时间留余量、`safety` 必含该目的地特有风险（如红叶季人多堵车、溶洞头盔、长城台阶陡）；
- **单源事实存疑原则（PoC 新增）**：只有一条语料提及的硬事实（票价、开放时间、里程），方案文字须用「以官方/现场公示为准」类措辞 hedging，不写成确定值；
- **合规原则（红线）**：方案文字必须**原创重写**——综合多条语料的事实，用自己的话组织；不抄原文句子、不出现作者名/平台/原文链接。语料引用（source+id）只存在于本地草稿，**不进入种子文件与数据库**；
- **画像解耦**：`drive.from` 恒为「家」，年龄不存数字，不写死任何用户画像信息（数据契约既有约定）。

## 四、数据契约

### 4.1 输入：语料（只读，本方案不改语料库）

字段见 [攻略流水线](攻略流水线.md) §三。本流程读取 `meta.json`、`text.md` 与 `corpus/index.jsonl`。

### 4.2 中间层：方案草稿 draft JSON（本地工作文件）

- 位置：`corpus/derived/<slug>.draft.json`（随语料库 gitignore，不进 git）；
- 作用：提取与审校的工作面，**唯一允许出现语料引用的地方**；
- `sources[].id` 必须用**完整 id**（如 xhs 的 24 位十六进制），不得用截短形式——校验工具按 id 定位语料原文（PoC 教训：摘要里的截短 id 会导致溯源断链）。

```json
{
  "slug": "labagoumen",
  "destination": "喇叭沟原始森林",
  "aliases": ["喇叭沟门", "喇叭沟"],
  "sources": [
    {"source": "xhs", "id": "…完整 id…", "url": "…", "used_for": ["红叶时间", "门票"]}
  ],
  "excluded": [
    {"source": "ctrip", "id": "…", "reason": "泛游记仅列名，误命中"}
  ],
  "facts": {
    "drive_to": "喇叭沟门满族乡", "drive_time_hint": "单程约 3 小时",
    "tickets": "门票 40 元（以官方为准）", "parking": "景区门口停车场",
    "intensity": "步道 3–5km 可选，爬升缓",
    "season": "10 月中下旬红叶",
    "age_fit": "5 岁+，可走 3km",
    "risks": ["红叶季周末拥堵", "山区比城区低 5°C 以上"],
    "highlights": ["白桦林", "原始次生林"]
  },
  "plan": { /* 完整 PLANS 条目（见 4.3），由 agent 起草、审校后定稿 */ },
  "status": "draft | reviewed | emitted"
}
```

### 4.3 输出：PLANS 种子条目（进 git）

- 全字段遵循 [数据契约](数据契约.md) §二；新增约束：

| 字段 | 语料派生方案的取值规则 |
|---|---|
| `id` | `derived-<slug>`（非日期 id，备用计划不参与月份归档排序） |
| `archived` | 恒为 `true`（进首页备用计划区，路线流水线跳过） |
| `type` / `theme` / `emoji` | 按内容选 A/B/C/D 周型与 SCENES 主题；不与既有方案扎堆 |
| `drive.from` | 恒为「家」；`drive.to` 必须可地理编码（正式地名） |
| `drive.time` / `drive.km` | 语料无精确值时给保守估计并留余量 |
| `hike` | 无徒步环节用 `null`（种子文件约定）；waypoint 的 `query` 用可编码锚点 |
| `badge` / `tasks` | 按 PRD-002 风格原创（观察自然类、零装备、3 条） |
| `review` | 固定 4 问模板（距离/孩子状态/问题教训/改进） |

- 落盘文件：新建 `data/data-e.js`（语料派生备用计划专用，与按月的 a–d 分开），`tools/dump-data.js` 的加载清单同步加入。

### 4.4 禁止项（校验工具强制）

1. 方案任何字段不得包含语料原文片段（校验：与所引语料做 n-gram 重合检测，≥8 字连续重合即拒绝；**目的地正式名与别名豁免**，避免专名误报）；
2. 方案任何字段不得出现作者名、平台名（小红书/微博/携程）、原文 URL；
3. 不得写入用户画像具体值（家位置、孩子小名等）；
4. 语料与 draft JSON 不进 git（`corpus/` 已 gitignore）。

## 五、实施步骤

新建 `tools/plan-pipeline/`（Python，与 guide-pipeline 同栈，不新增第三方依赖）：

| 步骤 | 工具/动作 | 输入 → 输出 |
|---|---|---|
| 1. 选料 | `select.py --dest "喇叭沟门" [--aliases a,b] [--out bundle.json]` | 目的地别名集 + 语料库 → 证据包 JSON（命中语料全文 + meta + 按互动数据/源优先级排序） |
| 2. 提取 | agent 会话读证据包 → 写 draft JSON（schema 4.2） | 证据包 → draft（draft 状态） |
| 3. 审校 | agent + 用户复核 draft：事实、强度、安全、原创性 | draft（reviewed 状态） |
| 4. 落盘 | `emit.py --draft <file>` | reviewed draft → 追加 `data/data-e.js` 条目（同 id 幂等跳过）+ draft 置 emitted |
| 5. 校验 | `validate.py [--check-data-e]` | dump-data 解析 + 契约字段校验（必填/枚举/类型/数组长度）+ 4.4 禁止项检查；全过才算完成 |

实施顺序建议：先 validate.py + emit.py（确定性、可测试），select.py 其次，提取模板最后。PoC 产出的 5 条 draft 作为工具的回归样例。
