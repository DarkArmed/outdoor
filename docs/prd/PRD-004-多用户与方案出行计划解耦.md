# PRD-004 · 多用户与方案出行计划解耦

> 编号：PRD-004 ｜ 版本：v1.0 ｜ 日期：2026-09-12 ｜ 状态：**已确认**
> 主题域：后端服务化中的多用户、持久化、公共方案与用户出行计划解耦。规范见 [prd/README](README.md)。

## 一、项目背景

PRD-001 已确认网站基础需求，并约定前后端分离阶段不实现登录、多用户、数据库。随着项目向可部署服务演进，需要：

1. 支撑多个用户（家庭）各自管理出行计划；
2. 用户数据从浏览器 `localStorage` 迁移到后端持久化存储；
3. 公共出行方案可被多个用户采用，但各自保留可配置项；
4. 为后续小程序、移动端提供可复用的 RESTful API。

本阶段**前端 `site/` 不动**，仅完成后端服务化能力。

## 二、术语

| 术语 | 英文名 | 含义 |
|---|---|---|
| 公共方案 | Plan | 共享的出行方案库，由现有 `PLANS` 导入，可随赛季更新优化。 |
| 出行计划 | Trip | 用户把公共方案加入自己日程后生成的独立行程，引用某个 Plan，并保存快照与覆盖项。 |
| 快照 | Snapshot | 创建 Trip 时从 Plan 深拷贝的内容，用于隔离方案后续变更。 |
| 覆盖项 | Overrides | 用户对本次 Trip 的个性化修改（出发位置、人数、偏好、自定义装备等）。 |

## 三、需求

### 3.1 用户与认证

| # | 需求 | 状态 |
|---|---|---|
| 3.1.1 | 后端支持用户注册（邮箱 + 密码），密码哈希存储 | 🔨 |
| 3.1.2 | 后端支持用户登录，返回 JWT | 🔨 |

| 3.1.4 | 每个用户拥有独立画像（Profile）：家庭位置、出行成员、孩子信息、出行偏好 | 🔨 |
| 3.1.5 | 用户只能访问自己的 Trip、状态、画像；公共方案只读共享 | 🔨 |

### 3.2 公共方案

| # | 需求 | 状态 |
|---|---|---|
| 3.2.1 | 后端提供 `/api/plans` 列表与 `/api/plans/{id}` 详情 | 🔨 |
| 3.2.2 | 公共方案字段与现有 `PLANS` 一致（见数据契约） | 🔨 |
| 3.2.3 | 后端初始化时从现有 `site/js/data/data-a|b|c|d.js` 导入公共方案 | 🔨 |

### 3.3 用户出行计划

| # | 需求 | 状态 |
|---|---|---|
| 3.3.1 | 用户可通过 `POST /api/trips` 从公共方案创建出行计划 | 🔨 |
| 3.3.2 | 创建 Trip 时自动复制公共方案内容生成 `snapshot` | 🔨 |
| 3.3.3 | Trip 支持 `overrides`，覆盖项优先级高于 `snapshot` | 🔨 |
| 3.3.4 | 公共方案后续更新不影响已有 Trip 的内容 | 🔨 |
| 3.3.5 | 用户可查询、更新、删除自己的 Trip | 🔨 |
| 3.3.6 | Trip 支持 `status`：`planned` / `done` / `archived` | 🔨 |
| 3.3.7 | Trip 支持 `planned_date`，用户可自由安排出行日期 | 🔨 |

## 六、明确不做的（边界）

- 本阶段**不通前端**，`site/` 仍走原有静态数据。
- 本阶段不做前端 React 重写、不做登录/多用户界面。
- 本阶段不在用户 home 变化时重新调用高德/Overpass 生成路线，直接复用已有 `ROUTES`。
- 不做真实 GPS 导航。
- 不做微信支付、短信、邮件等第三方服务集成。
