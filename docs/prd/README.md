# PRD 规范（产品需求文档）

> PRD 回答"**做什么**"：只写用户可验收的需求，不写实现机制（机制见 [docs/tech](../tech/README.md)）。
> 通用规则（隐私红线、版本号提交时升等）见 [docs/README](../README.md)。

## 命名

- 文件名 `PRD-001-简短主题.md`，编号三位递增、不回收；**一个主题域一份**（新主题域才开新编号）。

## 格式约定

1. **文档头**：`编号 · 版本 · 日期 · 状态`（草稿/已确认/已归档）+ 需求项状态图例行。文档头不写流程规则。
2. **需求项编号**：`x.y.z` 层级编号（如 2.1.3），讨论和施工时按编号引用，不用"那个功能"。
3. **状态标记**（全文统一）：✅ 已实现 ｜ 🔨 待实现 ｜ ⚠️ 部分实现/待验证 ｜ ❌ 已取消。
4. **文末必须有两节**：「待办清单」和「明确不做的（边界）」。

## 内容边界

- 只写**用户可验收的"做什么"**：判断标准是不写代码的人也能照着验收。
- **字段级内容属于需求**（如用户配置的每个字段），必须精确列出字段名和含义，不允许概括。
- 不写实现机制、技术选型、文件路径、版本历史。
- **不引用 ADR**：决策记录单向指向需求（ADR 里写"关联需求 PRD-xxx"），PRD 不反向引用，保持需求文档自洽。

## 改动流程

1. 改需求先改 PRD，再动代码；代码实现后回写需求项状态。
2. 版本号只在提交时升；未提交的改动不动版本号、不写修订记录。
